Beyond the Sessions

Eight workflows a PM cannot build with what our sessions taught, and the reference detail behind them. The existing decks cover setup, skills, subagents and multi-agent patterns. This one starts with what those pieces let you actually do: reports that write themselves overnight, context that stops going stale, checking a build yourself before you sign it off. Then it covers the parts that make those possible, including the undo button nobody knows exists.

Workflows worth building

The part that changes your week

Not commands. These are things a PM cannot do today with what the eight sessions taught, where the pieces already exist and nobody has put them together. Each one replaces a recurring manual chore. The commands are listed only as the parts you assemble, the same way the Skills session teaches a skill rather than teaching Markdown.

1. The recurring report writes itself before you wake up
Today
Every Monday you spend 45 minutes rebuilding the same competitive digest, or every Friday the same sprint summary. You do it by hand because it needs fresh input each time.
Instead
Take a skill you already wrote and turn it into a routine. It runs on Anthropic's cloud, so it fires whether your laptop is on or off, and delivers the finished digest to Slack or a branch. Your job changes from writing it to reacting to it.
a committed skill/schedulea connected repoa connector for delivery
Turns a weekly chore into a Monday-morning read.
How to do it
  1. Know where it runs, because that decides everything else. A routine created with /schedule executes on Anthropic-managed cloud infrastructure, so it keeps working with your laptop closed. The trade is that it works from repositories and connectors you attach, not from your local folder. If the job genuinely must touch local files, create a Local routine instead (Desktop app, Routines, New routine, Local), which is a Desktop scheduled task and does need your machine awake.
  2. Get it right by hand first. Run the skill interactively and check the output. A schedule multiplies whatever you already have, including the flaws, and you will not be watching when it runs.
  3. Commit what it needs. Each run clones the repo fresh, so the skill and any input files must be pushed. A skill sitting only in your local .claude/skills/ is invisible to the routine.
  4. Create it. Run /schedule and answer the questions about cadence, repositories and prompt. If your account has no GitHub access yet it will point you at /web-setup first. 
    /schedule

Every Monday at 7am, read competitive.md in this repo,
research each competitor listed there, and write a
digest with a source URL for every claim.
Send it to me as a Slack DM.
  5. Decide how the output reaches you, since it cannot write to your laptop. Either let it push to a claude/… branch, which is always accepted, or deliver through a connector like Slack or email. Note that MCP servers you added locally with claude mcp add do not carry over: add it as a connector on claude.ai, or commit a .mcp.json so it travels with the repo.
  6. Test it now, not on Monday. /schedule run triggers it immediately. /schedule list shows everything registered, and /schedule update changes one.
  7. Read the first real output before you trust it. Then fix the prompt, not the schedule. Most bad recurring output is a vague brief, not a broken cron.
Watch out: a green run status only means the session started and exited without an infrastructure error. It does not mean the task worked. Open the run and read the transcript, because blocked network calls and missing connector tools surface there, not in the status dot.
2. Your context files stop going stale
Today
Session 4 says put everything in knowledge folders, so you do, for two weeks. Then product-knowledge/ drifts from reality and every answer quietly gets worse, because keeping it current is manual and invisible.
Instead
A hook does the upkeep. One fires when a session ends and appends what changed to your work log or knowledge folder. Another fires at session start and loads today's brief. This repo already does exactly this with refresh-docs.sh, which is why its CLAUDE.md is never out of date.
SessionStart hookStop hookyour knowledge folder
The assembly line maintains itself instead of decaying.
How to do it
  1. Pick the moment. Stop fires when a turn ends, which is right for "record what just changed". SessionStart fires when a session opens, which is right for "load today's brief".
  2. Write the script at .claude/hooks/your-hook.sh and make it executable with chmod +x. Have it exit 0 quietly when there is nothing to do, so it never blocks a normal turn.
  3. Wire it up. Easiest path is /hooks, which walks you through it. The equivalent in .claude/settings.json is: 
    {
  "hooks": {
    "Stop": [{
      "hooks": [{
        "type": "command",
        "command": "bash .claude/hooks/your-hook.sh",
        "async": true,
        "timeout": 120
      }]
    }]
  }
}
    Use $CLAUDE_PROJECT_DIR/.claude/hooks/your-hook.sh instead if you want the path resolved absolutely regardless of where the session was started.
  4. Guard against a loop if your hook itself calls claude -p. Set an environment variable and exit early when it is already set, or the hook will trigger itself forever. This repo's refresh-docs.sh does exactly that, and is worth reading before you write your own.
  5. Prove it fired. Make a trivial change, end the turn, and check the result. Have the script append one line to a log file every run, so "did it run" is never a guess.
Watch out: a hook that fails silently looks identical to one that is working. The log line in step 5 is the whole difference.
3. Check the build yourself before you sign it off
Today
A ticket says Done. You either trust it, click through it manually, or wait for QA. When you find a bug you write the repro steps by hand and hope they are reproducible.
Instead
Claude drives the real product in a browser, walks the flow from your acceptance criteria, and reports what actually happened with screenshots at each step. A failed step becomes a bug report with exact repro steps, already written.
Playwright MCPChrome DevTools MCP/verifyyour acceptance criteria
You verify your own feature instead of taking Done on trust.
How to do it
  1. Connect a browser. Add the Playwright MCP or the Chrome DevTools MCP, then run /mcp and confirm it shows as connected before you go further.
  2. Hand it the acceptance criteria as numbered steps, plus the URL and how to log in. Keep credentials in .env and point at them, do not paste them into the prompt.
  3. Ask for observation, not a verdict. The wording matters: 
    Walk this flow one step at a time.
After each step, take a screenshot and tell me
what you actually SEE, and whether it matches
what step N expects.
Do not summarise or judge until the end.
  4. Turn each failure into a bug report. Ask for the exact steps to reproduce plus the screenshot at the failing step. That is a ticket an engineer can act on without a conversation.
  5. Re-run the same prompt after the fix. Because the steps are written down, your acceptance check is now repeatable instead of a one-off click-through.
Watch out: if you ask "does this work?", it will tend to say yes. Ask what it saw at each step, and let yourself decide whether that passes.
4. A raw export becomes a decision, not an afternoon
Today
A CSV of 2,000 support tickets or survey responses lands on you. You spend an afternoon in pivot tables, eyeball a few hundred rows, and present a guess about what people are asking for.
Instead
Claude reads every row, sorts them into a taxonomy you define, counts the trend month on month, and produces an interactive dashboard plus the deck. Because it reads all of them, the long tail stops being invisible.
a categorization skillsubagents for volume/dataviz
Every row read, not a sampled guess.
How to do it
  1. Put the export where Claude can read it, and if it contains customer data keep that folder out of git before you start, not after.
  2. Define the taxonomy yourself, first. Write the categories and one line on what belongs in each. If you let it invent buckets, they shift between runs and you can never trend the numbers month on month.
  3. Batch it if the file is large. Ask for subagents to process chunks and write intermediate results to files, so one long run cannot lose everything: 
    Categorise every row in data/tickets.csv using the
taxonomy in taxonomy.md. Process in batches of 200
with subagents, write each batch to
outputs/batches/, then merge.
Never invent a category outside taxonomy.md.
  4. Ask for counts before conclusions: volume per category, month on month, and the biggest movers. Then ask for the dashboard or deck off those numbers.
  5. Spot-check about 20 rows against their assigned category before you present anything. If the edge cases are wrong, tighten the taxonomy wording and re-run.
Watch out: the value here is that every row gets read. Do not let it sample "for speed" unless you asked for a sample and say so in the readout.
5. Answer "is this actually built?" without asking an engineer
Today
Your specs live in one place and the code in another. To check whether a business rule really shipped, or what the code does in an edge case your spec forgot, you ask someone and wait.
Instead
Add both directories to one session. Now you can ask Claude to compare the spec against the implementation and list every rule in the doc that has no matching code, and the reverse: behaviour in the code that no spec describes.
/add-diryour spec folderthe code repo
Spec-to-code drift becomes something you can audit yourself.
How to do it
  1. Start in your specs folder, the side you know best, then pull the code in rather than the other way around.
  2. Add the second directory: /add-dir /path/to/the-code-repo. Both are now readable in one session, with no copying between them.
  3. Ask for a mapping, one row per rule: 
    For every business rule in specs/billing.md, find
where it is implemented in the code repo.
Output a table: rule | file:line | IMPLEMENTED /
PARTIAL / NOT FOUND.
Cite file:line for every row. If you cannot find
it, say NOT FOUND rather than guessing.
  4. Run it in reverse. Ask what the code does that no spec describes. That direction is where the undocumented edge cases live, and it is the half people forget to ask for.
  5. Open two or three of the cited file:line references yourself. If the citations are real, the rest of the table is probably trustworthy. If they are not, stop and re-scope.
Watch out: treat NOT FOUND as "ask an engineer about this one", not as proof it was never built. Absence of evidence is not evidence of absence.
6. Your setup becomes the team's setup
Today
You build skills that save you hours. A teammate asks how, and the honest answer is "copy my folder and change the paths". Most of them never do, so the leverage stays with you.
Instead
Package your skills, hooks and commands as one plugin and host a marketplace. A teammate installs it with a single command and has your whole working setup, versioned. Claude can also generate the ramp-up guide from how you actually use it.
claude plugin inita marketplace/team-onboarding
One person's system becomes the team's default.
How to do it
  1. Pick only what is stable. Ship the three or four skills you use weekly and whose output shape has stopped changing. A half-finished skill costs your teammates more than it saves.
  2. Scaffold the plugin: claude plugin init <name>. It creates the structure for you, so you are not guessing at a manifest.
  3. Move the pieces in (skills, hooks, commands, MCP config) and install it locally first. Confirm each skill still triggers when it should, since paths often change in the move.
  4. Check the cost before you push it out. claude plugin details <name> shows the component inventory and the projected per-session token cost. If that number is high, trim before your team pays it on every session.
  5. Distribute it as a marketplace repo. A teammate adds the marketplace once and installs with a single command, and updates flow through the same way.
  6. Generate the ramp-up guide with /team-onboarding, which writes it from how you actually work rather than from what you remember to document.
Watch out: your skills probably reference paths from your repo. Test the install in a different project before handing it to anyone.
7. Long work runs while you are in meetings
Today
A deep competitive scan takes 20 minutes, so you sit and watch it, or start it and forget. Either way the terminal owns your attention.
Instead
Kick the work off in the background, go to your meeting, and get a notification when it finishes or when it needs a decision from you. A hook can fire that alert to your desktop or phone.
background agentsNotification hookRemote Control
Research runs on its schedule, not yours.
How to do it
  1. Brief it properly before you walk away. Anything vague will either stall waiting for you or confidently produce the wrong thing for 20 minutes. State the output file and the format up front.
  2. Send it to the background. Run /bg inside a session to move it into agent view, or press ← on an empty prompt to do both in one step. Ctrl+B pushes a running command or agent to the background.
  3. Know the limit: this runs on your machine, not in the cloud. Sleep pauses the work and it resumes on wake, but a full shutdown stops it. If it genuinely has to finish while your laptop is off, that is a cloud routine (workflow 1), not a background session.
  4. Get told when it matters. Add a Notification hook, which fires both when an agent needs input and when it completes: 
    {
  "hooks": {
    "Notification": [{
      "hooks": [{
        "type": "command",
        "command": "bash .claude/hooks/notify.sh"
      }]
    }]
  }
}
    Inside notify.sh, one line is enough: on macOS an osascript display-notification call, on Linux notify-send.
  5. For alerts away from the machine, enable Remote Control so it can push to your phone instead of a desktop banner you will not see.
  6. Come back through claude agents, which lists every session with its status, and attach to the one that finished or is waiting on you.
Watch out: a background session uses the same quota as an interactive one. Running five in parallel burns roughly five times the usage for that period.
8. Your three-hour session stops getting dumber
Today
Long sessions quietly degrade. Claude forgets a decision from an hour ago, repeats itself, or contradicts something you settled. So you start over and re-explain everything.
Instead
Treat context as a budget you can see and steer. Watch it fill, and when it gets tight compact the conversation while telling it what to keep, rather than clearing and losing the thread. Park reference material in files the session loads on demand instead of pasting it in.
/context/compact with instructionsload-on-demand files
The long working session stays as sharp as the first ten minutes.
How to do it
  1. Look at the budget early. Run /context near the start of a real working session so you know what normal looks like, rather than only checking once things feel wrong.
  2. Stop pasting reference material. Put the long document in a file and give Claude the path. It then reads what it needs, when it needs it, instead of carrying the whole thing all session.
  3. Compact with instructions, do not clear. Steer what survives: 
    /compact Keep every decision we made, the open
questions, and the file paths we are working in.
Drop the full file contents and the tool output.
  4. Use /btw for side questions ("what does this acronym mean") so a quick digression does not become permanent weight in a careful thread.
  5. Reserve /clear for genuinely switching task. If you clear by reflex and regret it, /rewind can now resume from before the clear.
Watch out: quality degrades well before the window is technically full. If answers start feeling vague or repetitive, that is the signal, not an error message.

1. Checkpoints and rewind

Not covered anywhere extends: Setup

The single biggest gap. Every session teaches plan mode as the way to stay safe before Claude acts, and nothing teaches the recovery path after it acts. People are running Claude Code believing there is no undo.

/rewind ★
Roll the conversation, your code, or both back to an earlier checkpoint. Claude Code checkpoints your files automatically as it edits, so you can step back to any earlier state.
Why it matters: this is the answer to "Claude just rewrote a file I needed". Most people reach for git or panic instead.
slashdocs / checkpointing
Esc Esc ★
Press Escape twice on an empty input to open the rewind menu directly. The fastest path to the same restore, with no command to remember.
Why it matters: a two-key undo is something people will actually use under pressure.
keysdocs / interactive-mode
/rewind past a /clear
Rewind can now resume a conversation from before you ran /clear, so a reflexive clear is no longer a one-way door.
Why it matters: the workshop actively teaches /clear as the reset button. This is the safety valve for that advice.
NEW v2.1.191docs / checkpointing
What rewind will NOT save you from ★
Five official limitations: changes made by bash commands are not tracked, subagent edits are not restored, external changes (your editor, a teammate) are not tracked, symlinked and hard-linked paths are not restored, and it is not a replacement for version control.
Why it matters: teach the limits with the feature, or people will trust it in exactly the multi-agent situations where it does not apply.
gotchadocs / checkpointing
claude --safe-mode
Start with every customization disabled: CLAUDE.md, plugins, skills, hooks and MCP servers. The clean-room baseline for "is it my config or is it Claude?".
Why it matters: once someone has 40 skills and a hook, this is the only sane first debugging step.
NEW v2.1.169docs / settings

2. Hooks, the deterministic layer

Named once, never taught extends: Skills

Skills and CLAUDE.md ask Claude to behave a certain way, and a model can always decide otherwise. A hook is a shell command the harness runs on an event, so it happens every time. This repo already ships one (.claude/hooks/refresh-docs.sh, a Stop hook that refreshes the docs after a turn changes source files), and no deck explains the mechanism.

Event Fires when PM use
PreToolUse Before a tool runs Hard-block edits to a protected file
PostToolUse After a tool succeeds Auto-format or lint what Claude just wrote
PostToolUseFailure After a tool fails Capture the failure for a retry loop
PermissionRequest A permission prompt is raised Auto-approve a known-safe pattern
UserPromptSubmit You hit enter Inject standing context into every prompt
Stop / StopFailure The turn ends Refresh docs, run tests, notify
SubagentStart / SubagentStop A subagent begins or ends Log or audit delegated work
PreCompact Before context is compacted Save state, or block the compaction
SessionStart / SessionEnd Session opens or closes Load a daily brief, write a work log
Notification Claude needs input or finishes Desktop or mobile alert on long runs
MessageDisplay An assistant message renders Transform or hide text as it displays
/hooks ★
View and configure hooks interactively instead of hand-editing JSON.
Why it matters: the entry point that makes hooks approachable for a non-engineer.
slashdocs / hooks
PreCompact can block
A PreCompact hook can stop a compaction by exiting with code 2 or returning {"decision":"block"}.
Why it matters: protects a long research run from being summarized at the worst moment.
NEW v2.1.105docs / hooks
continueOnBlock
A PostToolUse option that feeds the hook's rejection reason back to Claude and lets the turn continue, instead of just failing.
Why it matters: turns a hook from a wall into a correction. Claude learns the rule mid-turn.
NEW v2.1.139docs / hooks
hook args: string[]
Exec form that spawns the command directly with no shell, so paths with spaces never need quoting.
Why it matters: removes the most common reason a hand-written hook silently breaks.
NEW v2.1.139docs / hooks
DirectoryAdded
Fires after /add-dir registers a new working directory mid-session.
Why it matters: lets you auto-load that folder's conventions the moment it joins the session.
NEW v2.1.219docs / hooks
terminalSequence
A hook JSON output field that emits desktop notifications, window titles and bells without a controlling terminal.
Why it matters: the clean way to get "your agent finished" alerts from background runs.

3. Context engineering

Partially covered extends: Setup

The decks teach /clear and stop there. Context is the resource that decides output quality, and there are five more tools for managing it.

/context [all] ★
Shows how much of the context window is used, as a colored grid broken down by what is consuming it.
Why it matters: makes an invisible budget visible. Run it when answers start feeling vague.
slashdocs / costs
/compact [instructions] ★
Summarizes the conversation to free space while keeping the thread. The optional instructions steer what survives, e.g. /compact keep all the decisions and the open questions.
Why it matters: the difference between /clear (lose everything) and /compact (keep the thread). Most people only know the first.
slashdocs / costs
/btw <question>
Ask a side question that sees the full context but is not added to the conversation history, and has no tools. Press c to copy the raw markdown answer.
Why it matters: ask "what does this acronym mean" without polluting a careful research thread.
slashdocs / interactive-mode
/recap
A short summary of what has happened so far, generated for you when you come back to a session after time away.
Why it matters: PM sessions get interrupted constantly. This rebuilds your context, not Claude's.
NEW v2.1.108docs / interactive-mode
1-hour prompt caching
ENABLE_PROMPT_CACHING_1H opts into a 1-hour cache TTL on API key, Bedrock, Vertex and Foundry.
Why it matters: long sessions over a big repo get materially cheaper.
NEW v2.1.108docs / costs
/doctor CLAUDE.md trim check
A /doctor check that proposes trimming checked-in CLAUDE.md files by cutting content Claude could work out from the codebase itself.
Why it matters: every workshop CLAUDE.md grows until it hurts. This is the pruning tool.
NEW v2.1.206docs / memory

4. Models, effort and speed

Outdated in the decks extends: Setup, Agents

The decks say "Sonnet for most things, Opus when it is hard". The model lineup and the controls around it have both moved on.

Claude Opus 5 ★
Now the default Opus model (claude-opus-5), with a 1M context window and fast mode at $10/$50 per Mtok.
Why it matters: "Opus is the expensive one you avoid" is no longer the whole story. A 1M window changes what fits in one session.
NEW v2.1.219docs / model-config
Claude Fable 5.1 ★
Released 01-09-2026 (with Claude Mythos 5.1, the same model with different safeguards). The fable alias now resolves to it. 1M context, and Anthropic estimates about 25% less than Fable 5 for typical workloads. Not the default on any plan: opt in with /model fable.
Why it matters: the top of the lineup moved again in September. For a Pro-plan cohort the daily default is still Sonnet 5 at medium effort, Opus 5 for review passes, Fable only for tasks larger than one sitting.

Shows what each loaded skill costs in context and how often it is used, so you can turn off the ones you never call.

Why it matters: both replace "open the file and look" during a build, and both read well on a projector.

5. Guardrails that matter at scale

Not covered extends: Multi-Agent, Setup

The multi-agent deck teaches fan-out and warns that it costs roughly 15x a normal chat. It does not mention that Claude Code now ships hard caps to stop a runaway fan-out, or that sandboxing exists.

Runaway agent caps ★
Concurrent subagents are capped (default 20, CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS), as are spawns per session (default 200, CLAUDE_CODE_MAX_SUBAGENTS_PER_SESSION, reset by /clear) and web searches per session (default 200).
Why it matters: the direct answer to the cost fear the multi-agent deck raises. There is a floor under the worst case now.
NEW v2.1.212/217docs / settings
Sandboxed Bash ★
Run bash in filesystem and network isolation. Controls include sandbox.network.allowedDomains / deniedDomains / strictAllowlist, sandbox.credentials to block reading secrets, and sandbox.filesystem.disabled.
Why it matters: the real answer to "is it safe to let Claude run commands", which comes up in every session and is currently answered only with permissions.
NEW v2.1.187/216/219docs / sandboxing
Tool(param:value) rules
Permission rules can match a tool's input parameters, with wildcards. For example Agent(model:opus) blocks subagents from using Opus.
Why it matters: cost control as policy, not as a reminder. Cap the expensive model at the permission layer.
NEW v2.1.178docs / permissions
/less-permission-prompts ★
Scans your transcripts for the read-only Bash and MCP calls you keep approving, then proposes a prioritized allowlist for .claude/settings.json.
Why it matters: permission fatigue is the top reason people flip to bypass mode. This fixes the cause instead.
NEW v2.1.111docs / permissions
Auto mode and hard_deny
Auto mode classifies commands rather than matching patterns. autoMode.classifyAllShell routes every shell command through the classifier, and autoMode.hard_deny blocks unconditionally regardless of intent. Denial reasons appear in /permissions.
Why it matters: a middle ground between approving everything by hand and bypassing all prompts.
NEW v2.1.136/193docs / permissions
worktree.baseRef / bgIsolation
worktree.baseRef chooses whether worktrees branch from origin/<default> or local HEAD. worktree.bgIsolation: "none" lets background sessions edit the working copy directly.
Why it matters: the multi-agent deck teaches worktrees but not how to control where they branch from, which is the usual first surprise.
NEW v2.1.133/143docs / settings

6. Claude Code without a terminal

Not covered new session candidate

Every session so far assumes a human sitting at a prompt. The whole non-interactive surface, which is where automation actually lives, is untouched.

claude -p "query" ★
Print mode: run a query non-interactively and exit. Pair with --output-format json or stream-json for machine-readable output.
Why it matters: this is how a workflow becomes a script. One line turns any skill into something cron or CI can run.
clidocs / headless
cat file | claude -p "…"
Pipe a file or another command's output straight into Claude.
Why it matters: lets Claude sit in the middle of a normal shell pipeline, no project setup needed.
clidocs / headless
GitHub Actions and /install-github-app
Install the Claude GitHub App on a repo for PR reviews and automation, and run Claude Code inside GitHub Actions.
Why it matters: the bridge from "I use this locally" to "our repo uses this on every PR".
setupdocs / github-actions
claude ultrareview [target]
Runs /ultrareview, a parallel multi-agent cloud code review, non-interactively from CI or a script. Prints findings to stdout, --json for raw output.
Why it matters: a concrete multi-agent workflow that runs with nobody watching.
NEW v2.1.120docs / headless
Claude Agent SDK
Build your own agents on the same harness Claude Code runs on, in Python or TypeScript.
Why it matters: the honest answer to "can we productionize this?" once a PM's internal tool proves useful.
sdkdocs / agent-sdk
Remote Control, mobile and desktop
/desktop continues a session in the desktop app, /mobile shows a QR code, and with Remote Control enabled Claude can send mobile push notifications when it needs you.
Why it matters: long agent runs stop requiring you to babysit a terminal.

7. Workflows and session control

Not covered extends: Multi-Agent

Dynamic workflows are a newer orchestration layer above subagents, and a set of session commands that did not exist when the decks were written.

/workflows and workflow size ★
Watch a multi-agent workflow run live, with status filtering. A "Dynamic workflow size" setting in /config (or workflowSizeGuideline) steers how many agents Claude spawns, and a separate setting stops the word "workflow" in a prompt from triggering one.
Why it matters: the deck's biggest open question is "how do I control the cost of fan-out". This is the dial.
NEW v2.1.202/219docs / settings
